PAGE 8
● User story: As a student, I want to check a room’s availability so 
that I can choose a valid booking time.
● Build one responsive page for one selected room, with fictional 
booking data.
● The page checks availability only; it does not create or confirm 
bookings.
● Exclude login, database, backend, external API, payments and 
unrelated features.
Assignment #03
Scenario and scope

PAGE 9
● AC1. Candidate times are integer minutes after midnight: 0 <= 
start < end <= 1440; start must be strictly after now.
● AC2. Duration must not exceed 120 minutes. Exactly 120 minutes 
is permitted.
● AC3. Reject every request when the selected room is blocked.
● Assume now is valid (0–1439); use fictional data only.
Assignment #03
Required rules: AC1–AC3

PAGE 10
● AC4. Reject overlap with any existing booking. Intervals touching 
at an endpoint do NOT overlap.
● AC5. Display an unambiguous Available / Unavailable result; do 
not mutate existing bookings.
● AC6. Provide understandable validation feedback and a usable 
narrow/mobile layout.
● Treat these criteria as fixed: reject AI suggestions that change 
their meaning.
Assignment #03
Required rules: AC4–AC6

PAGE 11
● Before prompting AI, write the scope and acceptance criteria in 
your own words.
● Identify at least two likely failure points (for example, endpoint 
overlap and starts-now).
● Describe the function contract: can_book(start, end, now, 
blocked, existing).
● Record your initial assumptions and what will be verified 
manually.
